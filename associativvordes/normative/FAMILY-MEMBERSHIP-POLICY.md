# Политика членства — 1.0.0

## Конечная процедура

1. Зафиксировать `scope`: family_id, element_id, language, lemma_id, lexeme_id,
   sense_id, context_id. Неразрешённый ID — null, решение UNRESOLVED.
   Scope не является шаблоном или правилом для всех слов с таким написанием.
2. Установить оригинальную лемму, POS, словарную идентичность и значение.
   Омонимы разделять по lexeme ID; значения одной лексемы — по sense ID.
   Неразделённая частотная строка не подтверждает отдельные значения.
3. Для конкретного национального соответствия привести источник и точную
   область действия. Для косвенного пути перечислить все направленные шаги
   и свидетельства; общий дальний предок и транзитивность через омоним запрещены.
4. Проверить морфосемантическую связь с целевым элементом. Компонент сложного
   слова допустим при доказанных границах, роли и значении компонента;
   это не эквивалентность целой лексемы корню и не разрешение слияния семей.
5. Проверить все прежние решения и конфликтующие источники. Отсутствие записи
   или источника не доказывает отрицания. Сохранить отдельные статусы и reason.
6. Независимо оценить association_status. Для слабой/неизвестной опоры членство
   сохраняется, но пригодность для ассоциативного отбора не предполагается.

## Итоги и оси

| Итог | Условие |
|---|---|
| CONFIRMED_MEMBER | Установлены identity и sense, подтверждена допустимая связь и конечное национальное соответствие; проверяемые источники и авторизованное решение |
| CONFIRMED_NONMEMBER | Установлены identity и sense; доказана конкретная несовместимость/ложность связи, а не просто недостаток сведений |
| UNRESOLVED | Недостаточно доказательств, неясен смысл/ID/направление/соответствие либо нет авторизованного подтверждения |
| CONFLICT | Есть несовместимые установленные источники/текущие решения для пересекающегося scope; требуется арбитраж |

Независимые оси: evidence_status (`documented|insufficient|contradictory`),
lexical_identity_status и sense_status (`resolved|unresolved|conflict`),
relation_status (`supported|refuted|unresolved|conflict`), association_status
(`supported|weak|unknown|conflict`). Для каждой оси хранится список evidence IDs.
Свидетельство содержит источник, версию, locator, SHA-256 сохранённого утверждения,
finding, polarity и scope. Хеш утверждения не выдаётся за хеш всей веб-страницы.
Весь snapshot/источники/алгоритм/политика закреплены отдельными SHA-256.

## История и переходы

Решения append-only. Нельзя заменить excluded/uncertain из v6 на положительное
из-за нового alias, корпуса, языка, модели или source confidence. Отрицательное
legacy-решение с lemma-level scope блокирует и более узкие значения той же
лексемной строки, пока отдельное подтверждённое уточнение scope не разрешит его.
Неизвестный sense в старом отрицании означает охват строки, а не отсутствие запрета.
Иная семья/язык/lemma не наследуют запрет. Quarantine family-level действует
на все её значения в указанном языке; снятие требует отдельного решения.

Противоречащее отрицанию положительное предложение даёт CONFLICT.
Снятие запрета требует авторизованного supersession с точными ID старых решений,
новым scope, основанием и сохранением прежних записей. `supersedes` во входном JSON
само ничего не разрешает. Верификатор должен подтвердить отзыв/замещение.
Неконфликтующее отсутствие подтверждения остаётся UNRESOLVED.

## Адаптация существующих статусов

v5 `safe_automatic`, `verified`, source confidence и наличие materialized row
сами не отображаются в CONFIRMED_MEMBER. v6 `accepted` можно перенести только
после проверки binding/edge/sense/provenance и действующих grants; legacy exact
proof отдельно пересматривается. `excluded` сохраняет запрет; `uncertain/pending`
не превращается в отрицательное лингвистическое подтверждение. Разметочные
yes/no/uncertain и PROPOSE_INCLUDE/PROPOSE_EXCLUDE/ABSTAIN — входные утверждения,
а не автоматическая сертификация. Файлы старых исключений не переписываются.

## Достаточность для автоматического исправления

Необходимо: подтверждённое конечное решение о конкретной связи, установленная
идентичность и смысл, проверенные исходные данные и source-lock, сохранённые
отрицательные ограничения, отсутствие конфликтов, точные before/after и scope,
полная история, неизменный parent snapshot и нормативная версия.
Допустимые классы — существующие ADD_MEMBER, EXCLUDE_MEMBER, CORRECT_RELATION,
CORRECT_IDENTITY, CORRECT_FAMILY; каждое поле изменения должно быть разрешено.
Создание/признание корня, распространение по подстроке и изменение формул запрещены.

Автоматически исполняется только уже разрешённая операция, а не самостоятельное
лингвистическое решение модели. Требования `release_control` остаются обязательны:
два независимых текущих человеческих подтверждения конкретной операции,
подписи, независимая проверка, quality/calculator gates и owner approval.
Результат локального eligibility никогда не заменяет эти разрешения.
В данном этапе нет разрешённых операций или применения к семьям.
