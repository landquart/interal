## Граница доверия

Внешний проверяющий загружает неизменяемые источники и журнал решений, проверяет
подписи и область действия, затем передаёт `verifiedEvidenceIds`,
`authorizedDecisionIds`, `authorizedSupersessions` в чистые функции.
Обязательны также доверенные Map `verifiedEvidenceDigests` и
`authorizedDecisionDigests` (ID → `digest` полного объекта). Одних ID недостаточно:
изменение scope, reason, источника или смысла требует новой авторизации.
Для современной опоры дополнительно нужен проверенный внешний результат
`verifiedAssociationDecisionIds`, привязанный к тому же решению и свидетельствам.
Значения из входного JSON нельзя использовать как этот доверенный контекст.
Тестовый контекст в suite моделирует проверяющего и не имеет полномочий записи.
`test_fixture` отключён по умолчанию; `allowTestFixtures=true` допустим только
в тестах, никогда в рабочем адаптере.

`evaluateMembership` ничего не измеряет и не записывает. `assessRecognition`
проверяет необходимые численные условия по уже рассчитанному внешнему результату,
но не присваивает корню нормативный статус. `automaticCorrectionEligibility`
возвращает только допуск к подготовке плана: фактическое применение остаётся за
`release_control` с его проверками, reviewer/blind/verifier/owner и подписями.
Совпадение моделей, `confidence`, `verified: true` или валидный JSON полномочий не дают.

Изменение нормативного смысла требует новой major-версии и повторной проверки
затронутых решений; добавление тестов без изменения политики — patch. Старые
решения и отрицательные ограничения не удаляются при смене версии.
