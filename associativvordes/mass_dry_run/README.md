# Полный исследовательский dry-run — этап 06

Команда выполняет весь цикл по реальным сертифицированным входам: заморозка → пять ступеней → независимый полный повтор → проверка истории/восстановления → snapshot и ручные очереди. **Ни одно предложение не применяется к production.** Сеть генерации отключена; допустим только конфиг с providers={}, max_requests=0, allow_paid=false. Ключи не нужны.

## Область

В закреплённом shadow v6 реестре 19 canonical семей. Он взят из сертифицированной проекции, а не из отображаемого ограниченного списка и не из миллионного production v5 инвентаря. Источник v6 закреплён receipt реестра и Git blob IDs; исходная ветка v6 может отличаться от production/main. PEDE разрешается настоящим alias в canonical family:ped. Никаких новых ID и автоматического переключения v5/v6.

Полный native-граф — существующий certified index: миллионы исходных лексем/дуг всех закреплённых источников и шести языков. Инфлекции хранятся отдельно и проверяются через auxiliary, без превращения их в деривационные дуги. Маленький frozen pilot graph не подменяет этот индекс.

Результаты полного текущего цикла: [отчёт](../../audit/associative-external-preparation/mass06-dry-run/REPORT.md). Покрытие всех 19 семей этого реестра **не является покрытием всех production v5 семей или всех слов языка**.

## Запуск

Python 3.12+, Linux/POSIX с flock/fsync/wait4, подготовленные входы этапов 01–02. Работа только с исходными неизменёнными источниками и отдельными исследовательскими каталогами.

```bash
python3 associativvordes/mass_dry_run/run.py \
  --index /srv/interal-research/index/index.sqlite \
  --registry /srv/interal-research/registry/registry.sqlite \
  --aux /srv/interal-research/aux/aux.sqlite \
  --project /srv/interal-research/project/project.sqlite \
  --source-lock data/morphology-evidence/sources/source-lock.json \
  --release /srv/interal-research/certified-release \
  --prior-queue /srv/interal-research/prior-mass-queue/preview.sqlite \
  --review-ledger /srv/interal-research/current-review-ledger \
  --output /srv/interal-research/dry-run06/run-01
```

Требуется **новый** output вне checkout и вне входных каталогов. Команда не скачивает данные и не повторяет сертификацию незаметно. Проверяет SHA баз и receipts, соответствие catalog build ID, версии источников, все normalized snapshots, исходную историю, tracked-файлы проекта и модули алгоритмов. Все длительные задания выполняются отдельными процессами, stdout/stderr и ресурсные receipts сохраняются в jobs.

FROZEN-INPUTS.json содержит commit checkout, собственную версию оркестратора через hashes модулей, отдельный исходный commit/manifest реестра, source-lock, каталог, конфиг, бюджеты, исторические состояния и контрольные суммы защищённых файлов. Это разные виды provenance: commit проекта не переименовывает старую сертифицированную версию реестра в новую.

Не запускайте редакторы решений над входным ledger/queue во время эксперимента. Любое изменение защищённого состояния останавливает проверки. Рабочие очереди, annotation stores, восстановленные stores и новый review-ledger создаются исключительно под output.

## Ступени и проверки

Протокол [protocol06.json](protocol06.json) зафиксирован заранее. Для 19 семей округление 1% и 5% даёт неудобные одинаковые/нулевые наборы, поэтому выбраны фиксированные слои:

1. REGUL, PEDE, INTER, все шесть языков, уменьшенные лимиты на seeds/source/class/depth.
2. REGUL, все языки, обычные bounded budgets: 1 из 19 семей.
3. REGUL + PEDE: 2 из 19.
4. REGUL + PEDE + INTER + ALTER + LIBER: 5 из 19.
5. Все canonical семьи реестра.

Точные доли публикуются, названия approx не выдаются за точные 1%/5%. Представительный первый слой использует меньше кандидатов за счёт ограничений, хотя затрагивает три трудные семьи. Budgets каждого слоя закреплены; независимый повтор полного слоя использует точно те же настройки.

Перед следующей ступенью должны пройти инженерные проверки:

- целостность семейной области, ID, исходных значений, языка и POS;
- отсутствие чужого native-пути и неподтверждённого межъязыкового перехода;
- запрет инфлекции как производности и расширения по подстроке;
- сохранность scoped-отрицаний и отсутствие выдуманной независимости источников;
- ноль API-запросов и production writes;
- время, действительный ru_maxrss дочерних процессов, логический и выделенный объём диска;
- лимит 2 GiB на процесс и 8 GiB рабочего output на ступень;
- восстановление после SIGKILL и после частичного discovery checkpoint;
- неизменность истории, aliases, lexical heads, memberships и tracked-файлов/формул.

Структурные проверки не заменяют семантическое gold-измерение. Инженерный PASS разрешает продолжение **только dry-run с обязательной ручной проверкой**. Отсутствующий gold остаётся BLOCKED и не даёт допуск к изменениям.

## Реальное прерывание и повтор

На каждой ступени второй annotation процесс получает SIGKILL после fsync нескольких завершённых предложений. Новый процесс открывает тот же store; проверяются число пропущенных уже записанных результатов, весь итоговый snapshot и отсутствие дубликатов. Для discovery создаётся отдельный частичный поиск: он не должен опубликовать CURRENT.json; resume обязан получить такой же manifest/version.

Полный независимый повтор использует новые search DB и annotation store, а не кеш первого процесса. Сравниваются questions/IDs, классификации, собственные native paths, evidence refs/raw rows, группы, история и discovery manifests. Времена, run IDs и предыдущие result refs отделяются от детерминированной части. Реальные ответы LLM здесь отсутствуют: их недетерминированность помечается NOT_RUN, а не «нулевое расхождение».

Annotation-backup содержит всю authority-историю и проверяется настоящим restore в новый каталог. Existing review интерфейс импортирует отдельный handoff: ни одного события решения человека при этом создаваться не должно. Подробнее про приватные stores и backup — [модуль 05](../auto_annotation/README.md).

CHECKPOINT.json верхнего уровня фиксирует законченные ступени. Отдельный контроллер finish.py проверяет hashes исходных модулей и законченных snapshots, повторно проверяет входы и завершает публикацию. Его собственный hash регистрируется до использования; исходные алгоритмы и пороги не переписываются. Незаконченная ступень сохраняется, а для её повтора создаётся новый рабочий каталог. Завершённый архив повторно не пересчитывается.

```bash
python3 associativvordes/mass_dry_run/finish.py \\
  --output /srv/interal-research/dry-run06/run-01 \\
  --release /srv/interal-research/certified-release
```

--wait позволяет дождаться завершения ещё работающего исходного координатора. Не запускайте два других пишущих процесса в одном output. При повреждённом backup или незавершённом предыдущем restore контроллер останавливается с конкретной ошибкой и сохраняет прежние файлы. Для совершенно независимого полного эксперимента по-прежнему нужен новый output.

## Группы результата

Файл final/SNAPSHOT.json содержит все вопросы и native-предложения, индекс карточек с путями, реальные исходные строки и отдельные списки ID:

- potential_additions — гипотезы нового членства из обнаружения;
- potential_exclusions — предварительный аудит существующих записей с историей и/или guard; само наличие истории не доказывает противоречия и не оправдывает исключение;
- relation_type_audit — спорный или ещё не установленный тип связи;
- identity_unresolved — сомнительная лексическая идентичность;
- interfamily_conflicts — конкурирующие семейные анализы;
- possible_bases — обратные гипотезы основы, без нового canonical ID;
- source_analysis_conflicts — возможные конфликты исходных анализов;
- preserved_existing_decisions — сохранённая история, **не новое семантическое подтверждение**;
- confirmed_existing_decisions — только действительно подтверждённые решения; без gold список пуст;
- manual_review — обязательная ручная очередь.

Группы пересекаются: сумма длин не равна числу кандидатов. Действительно предложенные моделью include/exclude и изменения типа вынесены отдельно в actual_semantic_proposals. ABSTAIN не подменяется REJECT; гипотеза исключения не удаляет запись.

Исходные идентификаторы и связь вопрос→native-лексема сохраняются. Публичная форма удаляет keyed-персональные поля через существующий scrub, полная исходная история остаётся в приватном frozen/input/store. Перед внешней публикацией собственных пользовательских историй дополнительно проверяйте свободный текст и вложенные legacy-массивы: они могут содержать личные данные.

## Качество и пороги

При наличии настоящих человеческих данных: --judgments и --roster существующего контракта gold из этапа 04. Ни исходное accepted, ни корпусный status, ни алгоритмический путь/LLM не становятся gold. Сопоставление mass→pilot возможно только по family + language + native ID, без склеивания написаний; публикуется фактическое число таких совпадений.

Протокол 04 сохраняется: precision lower bound 0.99, false merge upper bound 0.001 с заданной поправкой на 12 заранее определённых strata. Они не ослабляются под текущие результаты. Без gold знаменатель пригодных проверок равен нулю, precision/ошибки/CI — unknown/null, а не 100% точность или нулевая семантическая ошибка.

Формируются две дополнительные выборки: 60 псевдослучайных по закреплённому seed и 60 риск-ориентированных с балансировкой family/language. Публикуются точные IDs, пересечение, число уникальных случаев и требуемых независимых человеческих проверок. Задания слепые к результатам алгоритма, без заполненных ответов.

QUALITY.json перечисляет конкретные BLOCKED-проблемы, допустимые технические операции и запрет семантического применения. Наличие операторских инженерных проверок не означает, что человек уже оценил слова.

## Артефакты и тесты

CYCLE.json — все ступени и ресурсы; REPEAT.json — сравнение независимых прогонов; INTEGRITY.json — защищённые состояния; RESTORE.json — восстановление; QUALITY.json — gold/пороги/выборки; final/*.json — отдельные очереди; review-handoff — реальный импорт для интерфейса; PACKED-PROPOSALS.json.gz — lossless DAG archive полного snapshot, QC tasks и frozen registry state. ARCHIVE.json закрепляет hashes и проверку точных JSON bytes.

```bash
python3 -m unittest discover -s associativvordes/mass_dry_run -v
node --test tests/associative-mass-dry-run.test.mjs
python3 associativvordes/pilot_evaluation/archive04.py \
  /srv/interal-research/dry-run06/run-01/PACKED-PROPOSALS.json.gz \
  /srv/interal-research/dry-run06/unpacked-01
```

27 новых тестов используют явно TEST_ONLY fixtures для границ/контрактов; это не разметка языка. Полный прогон требует настоящих certified индексов, поэтому обычный CI проверяет контракты и регрессии, а измеренные массовые receipts сохраняются отдельно. API cost равен нулю только для реально отсутствующих запросов; стоимость вычислительной инфраструктуры и будущей LLM обработки без выбранной модели не выдумывается.


## Карточки из опубликованного snapshot

После unpack можно открыть все вопросы в существующем интерфейсе, не пересчитывая граф:

```bash
python3 associativvordes/mass_dry_run/export_snapshot.py \\
  --snapshot /srv/interal-research/dry-run06/unpacked-01/SNAPSHOT.json \\
  --output /srv/interal-research/dry-run06/review-export-01 \\
  --ledger /srv/interal-research/dry-run06/review-ledger-01
```

Оба каталога должны быть новыми и находиться вне checkout. --expected-sha256 принимает checksum исходных JSON bytes из ARCHIVE.json (не semantic snapshot hash из REPEAT). Исходные строки автоматически прикрепляются к новому ledger; существующий ручной ledger не перезаписывается. Далее запустите review/server.py по его [RUNBOOK](../review/RUNBOOK.md). Импорт не создаёт решений человека, blind роль по-прежнему не получает automated_proposals.
