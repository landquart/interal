# План исправлений после независимого аудита

Проверенный исходный SHA: `b266c92f00d111c1df53da05221fefac0db1dc3a`. Данный PR содержит только отчёты. Следующий исполнитель сначала обновляет remote/production, читает CHECKPOINT.md и не повторяет доказанные проверки без изменения файлов.

## Этап 0 — Зафиксировать предмет исправления

1. Сопоставить новый head/production с LIVE-ASSETS.txt; выделить актуальные AC-ID.
2. Получить исходное сохранённое состояние regul с targetMeaning, candidate word/model IDs, primary/review, review_required, intervals и diagnostics. Не требовать ключи пользователя.
3. Получить безопасные backend/upstream traces для invalid primary/403; не публиковать credentials/raw пользовательские данные. Установить слой, вернувший 403, прежде чем менять timeout/model.
4. Завести отдельную ветку исправления от актуального main; сохранить v5 production routing и существующие PR.
Готовность: воспроизводимый исходный run или честно зафиксированное отсутствие state; план кода привязан к AC-ID.

## Этап 1 — Восстановить реальное подключение v5 (AC-001, AC-012)

Зависит только от этапа 0. Устранить двойной transport: внедряемый fetch должен поддерживать тот же raw gzip/JSON контракт, что прямой FamilyIndexLoader. Сохранить abort/cache/fanout/blocked-family guards; нельзя обходить их через случайный резервный поиск. Сделать provenance ошибки/резервного режима видимой. Не добавлять/удалять memberships, не изменять snapshot индекса.

Готовность: createCandidateIndexLoader и реальная страница читают gzip production-like без family_index JSON error; regul/en возвращает два curated corpus records проверенного snapshot, а не 152 fallback entries. Все шесть языков сравниваются с данными **актуального** snapshot. Отдельно предлог inter остаётся в документированном registry/static route. Нет переключения на v6.

## Этап 2 — Стабилизировать схему данных и отображение (AC-002, AC-005, AC-010)

Можно выполнять после определения контрактов этапа 0 независимо от внешнего Qwen.
- Явные поля demographicSpeakers/included/completion/reviewState (названия окончательно выбрать в реализации), N доступен каждой строке.
- Неполные weighted contributions показываются как отсутствующие, без NaN.
- Null-safe numeric persistence; настоящий ноль сохраняется нулём, отсутствие остаётся null. Старые нули, созданные дефектом, не объявлять измеренными без provenance; требовать recalculation при неоднозначности.
- Подписи RU/EN: max P и A представителя; найдено/выбрано/оценено/включено различаются.

Готовность: таблица с pending A содержит справочные N, предварительный P, понятную причину отсутствия подтверждённого A; сохранение/восстановление не изобретает показатели; формулы FA/P/A не изменены.

## Этап 3 — Исправить lifecycle и диагностические причины (AC-003, AC-004, AC-006, AC-007, AC-008)

Зависит от схемы этапа 2.
- Execution completion отделить от verification required и acceptance. Успешное завершение запросов не выдавать за принятие.
- Настоящие callbacks reviewing до запроса; исправить перекрывание status spread.
- Ручной анализ использует run/candidate token и cancellation. Старый catch/results не мутируют новый run.
- Cache signal policy проверяется при двух параллельных consumers.
- Deadline покрывает fetch+body+parse; upstream cancellation/timeout документируются. Не выбирать timeout произвольно на основании одного замера.

Готовность: сценарии нового запуска, reset, редактирования/удаления ручной строки и late responses проходят; terminal states объясняют нужду в review/ошибку/отсутствие кандидатов отдельно. Ни одна из правок не разрешает принимать отсутствующий review.

## Этап 4 — Backend contract и эксплуатационная диагностика (AC-009)

Зависит от trace из этапа 0, может идти отдельно от этапа 1.
Проверять semantic fields на сервере до ok:true; возвращать типизированные ошибки. Установить, вызван invalid payload extraction/schema/model response или другой причиной. Отдельно выяснить 403. Сохранить whitelist моделей, формулы и роль первичной/повторной оценок.

Готовность: invalid semantic data не маскируется HTTP200-success; клиент показывает точную стадию/причину и сохраняет успешную primary при ошибке review как preliminary. Upstream причина подтверждена, либо остаётся явно открытой.

## Этап 5 — Отдельные методологические решения (AC-011, AC-013, AC-015)

Зависит от этапа 0; не является разрешением автоматически менять методологию.
Нужны письменные решения:
- конечный ноль против отсутствия данных при represented/denominator;
- область полноты: selected, все модели, слабые selected с отсутствующим review;
- допустимость принятия при неполной Qwen candidate validation и имеющихся независимых этимологических доказательствах;
- требования к устойчивости представителя и интервалам.

Готовность: каждое решение имеет источник, дату и утверждённые контрольные случаи; только затем отдельная реализация. Сохраняется max-P/тот же A representative, пока правила не изменены явно.

## Этап 6 — Независимая верификация

После всех разрешённых изменений:
1. Проверки AC-ID из ISSUES.md, включая page route с реальными gzip headers.
2. Сравнение regul, nat, loc, inter, отсутствующего корня: full, partial, unconfirmed, index error, primary error, review error, abort, restored state.
3. Live production-like run с фиксированным meaning и записью selected derivatives, P/A/review/FA/N/statuses; не выдавать mocks за живой сервис.
4. Целевые существующие проверки, затем полный required CI; AC-014 расследовать отдельным изменением PH, не подгонять ожидания в ассоциативном PR.
5. Доказать отсутствие непредусмотренных изменений методологии/данных/frequency/lemma IDs и v5→v6 переключения.
6. Сохранить SHA, provenance, результаты и остаточные ограничения в новом checkpoint.

Готовность: для всех первоначальных симптомов есть before/after evidence; нет NaN и fabricated null→0; недоступный review блокирует принятие с точной причиной; полные данные дают FA/A по утверждённому denominator. PR публикуется для проверки, merge/production publication только в отдельно разрешённом этапе.
